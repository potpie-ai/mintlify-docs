title: "Code Generation Agent"
---

The Code Generation Agent reads your codebase's existing patterns and conventions before writing a single line, then generates code that fits naturally into what already exists.

if specific `node_ids` are referenced in the query, it fetches their source code and appends it as code context.

## How It Works

### Understand the Task

The agent classifies every incoming task into one of five types: 
- **new feature**
- **modification** 
- **refactor**
- **bug fix** 
- **multi-file change**
 
 It extracts target files, classes, functions, scope, and dependencies.

<Note> For **multi-file or complex tasks**, it upfront identifies all impacted files and determines the order changes that need to happen, and thereby resolving dependencies for the files . </Note>


### Explore the Codebase

The agent reads the codebase prior to writing anything:

- `ask_knowledge_graph_queries` : finds where the relevant feature or functionality lives
- `get_code_file_structure` : understands directory layout and module organization
- `get_code_from_probable_node_name` : retrieves specific named classes or functions
- `get_code_from_multiple_node_ids` : batch-fetches all relevant nodes collected so far
- `get_node_neighbours_from_node_id` : maps all call relationships
- `fetch_file` / `fetch_files_batch` : retrieves full files or specific line ranges
- `web_search_tool` / `webpage_extractor` : retrieves domain best practices when relevant
- `get_nodes_from_tags` : used as a last resort if no relevant files are found

### Analyze Patterns

Prior to  writing, the agent captures exact indentation, import order, naming conventions, string literal formats, and docstring style from the existing codebase.

It maps every import that needs to change, identifies all impacted files including tests, and documents any database schema or API contract changes.

### Write Code

Changes are written through the **Code Changes Manager** (a Redis-backed session). The agent begins by calling `checkout_worktree_branch`, which creates or reuses a dedicated branch named `agent/edits-{sanitized_conversation_id}`.

The conversation ID is sanitized before branch creation by replacing forward slashes, backslashes, and spaces with hyphens to ensure the branch name is valid and safe. Changes are then written using:
- `add_file_to_changes` : for new files
- `update_file_lines`, `replace_in_file`, `insert_lines`, `delete_lines` : for modifications

Before every line-based operation, the agent calls `get_file_from_changes` with `with_line_numbers=true` so it always works against the current state of the file and never assumes line numbers after a prior insert or delete.

<Note> After every operation, it re-fetches to verify the change applied correctly.</Note>

### Review and Apply

The agent calls `show_diff` to display all changes as unified diffs, then immediately invokes `apply_changes`to persist them.
Until `apply_changes` is executed, all changes exist only within the Redis session and are not written to disk.

**PR creation** only happens upon explicit user confirmation. The agent presents the **diff**, asks the user to confirm, and waits. Upon confirmation, it calls `create_pr_workflow`, a single composite operation that applies the patches, creates or updates the branch, commits the changes, pushes them to the remote repository, and opens a pull request on GitHub or GitLab.

## Calling the Agent
```bash
curl -X POST https://localhost:8001/api/v2/conversations/ \
  -H "x-api-key: YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "project_ids": ["proj_abc123"],
    "agent_ids": ["code_generation_agent"]
  }'
```

Once you have a `conversation_id`, send your instruction:
```bash
curl -X POST https://localhost:8001/api/v2/conversations/conv_xyz789/message/ \
  -H "x-api-key: YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "content": "Add rate limiting to the authentication endpoints",
    "node_ids": ["node_abc123"]
  }'
```
